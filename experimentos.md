# Experimentos

## 01 — Pool de conexões

- **Hipótese:** reutilizar até 10 conexões com `pg.Pool` deve reduzir a latência e a CPU do banco, evitando abrir e fechar uma conexão PostgreSQL para cada consulta. A resposta da API deve permanecer igual.
- **Fonte da hipótese:** [node-postgres — Pooling](https://node-postgres.com/features/pooling). A documentação explica o custo de handshake por conexão e recomenda pool para aplicações que fazem consultas frequentes. O tamanho 10 é o padrão documentado em [Pool API](https://node-postgres.com/apis/pool); será definido explicitamente neste experimento.
- **Antes:** três execuções de `00-linha-de-base`, com `VUS=20`, `DURACAO=60s` e `SEMENTE=42`: [113816](resultados/20261106-113816-00-linha-de-base/), [114000](resultados/20261106-114000-00-linha-de-base/) e [114143](resultados/20261106-114143-00-linha-de-base/).
- **Depois:** três execuções de `01-pool`, com os mesmos parâmetros: [155042](resultados/20261106-155042-01-pool/), [155548](resultados/20261106-155548-01-pool/) e [155750](resultados/20261106-155750-01-pool/). Todas tiveram `0.00%` de erros e terminaram com “Contrato mantido”. Uma execução interrompida, sem verificação de contrato completa, foi descartada.
- **Status:** aplicada e medida.
- **Conclusão:** as medianas passaram de 2,39 para 2,86 requisições/s (+19,7%) e de 26.801 ms para 25.227,2 ms no p95 geral (-5,9%). A mediana de CPU média do banco caiu de 100,2% para 99,3%, ainda perto do limite. A memória média da API subiu de 35,2 MiB para 38,3 MiB. Na rota `/clientes/:id/pedidos`, o p95 mediano foi de 28.557,3 ms para 30.030,7 ms; o pool, sozinho, não resolveu esse gargalo. A variação de memória do banco entre execuções foi alta, então não concluímos economia de memória.

## 02 — Consulta única para pedidos do cliente

- **Hipótese:** substituir as consultas sequenciais de pedidos, itens e produtos por uma consulta com `LEFT JOIN` deve reduzir as viagens entre API e banco e o p95 de `/clientes/:id/pedidos`, sem mudar status, campos, valores ou ordem da resposta.
- **Fonte da hipótese:** [Turcotte, Aldrich e Tip, “reformulator: Automated Refactoring of the N+1 Problem in Database-Backed Applications”, ASE 2022](https://doi.org/10.1145/3551349.3556911). O estudo descreve consultas dentro de loops como N+1 e avalia refatorações que reduzem o número de consultas; os autores também recomendam verificar o comportamento após a transformação. O estudo usa Sequelize, enquanto esta API usa SQL direto, portanto é uma justificativa para testar, não uma previsão do ganho.
- **Antes:** três execuções da versão com pool: [155042](resultados/20261106-155042-01-pool/), [155548](resultados/20261106-155548-01-pool/) e [155750](resultados/20261106-155750-01-pool/). Na rota `/clientes/:id/pedidos`, o p95 mediano foi 30.030,7 ms.
- **Depois:** três execuções de `02-pedidos-join`, com os mesmos parâmetros: [160657](resultados/20261106-160657-02-pedidos-join/), [160838](resultados/20261106-160838-02-pedidos-join/) e [161023](resultados/20261106-161023-02-pedidos-join/). Todas tiveram `0.00%` de erros e terminaram com “Contrato mantido”.
- **Status:** aplicada e medida.
- **Conclusão:** comparada à versão com pool, a mediana subiu de 2,86 para 4,21 requisições/s (+47,2%). O p95 geral caiu de 25.227,2 ms para 10.916,1 ms (-56,7%), e o p95 de `/clientes/:id/pedidos` caiu de 30.030,7 ms para 11.155,5 ms (-62,8%). A CPU média do banco permaneceu praticamente igual (99,3% para 99,4%), enquanto a memória máxima mediana do banco subiu de 479,0 MiB para 502,4 MiB, perto do limite de 512 MiB. A mudança acelerou a API nesta carga, mas não reduziu a saturação de CPU e elevou o pico de memória observado; esse custo precisa ser acompanhado nos próximos experimentos.

## 03 — Índices para pedidos do cliente

- **Hipótese:** índices B-tree em `pedidos(cliente_id, criado_em DESC, id DESC)` e `itens_pedido(pedido_id, id)` devem evitar as leituras sequenciais observadas no plano da rota com JOIN, reduzindo o p95 de `/clientes/:id/pedidos` e a carga do banco. O custo é espaço em disco e manutenção dos índices.
- **Evidência anterior:** [planos e índices antes do teste](diagnostico/03-planos-antes-indices.txt). A consulta JOIN fez leitura sequencial de 500 mil pedidos e 1,5 milhão de itens, com tempo de execução de 4.706 ms para o cliente analisado; só as quatro chaves primárias apareciam em `\\di`.
- **Fonte da hipótese:** [documentação PostgreSQL 16 — índices](https://www.postgresql.org/docs/16/indexes.html) explica o benefício e o custo geral de índices; [índices multicoluna](https://www.postgresql.org/docs/16/indexes-multicolumn.html) explica a utilidade de colocar primeiro a coluna filtrada (`cliente_id` ou `pedido_id`) e depois as colunas de ordenação.
- **Antes:** três execuções de `02-pedidos-join`: [160657](resultados/20261106-160657-02-pedidos-join/), [160838](resultados/20261106-160838-02-pedidos-join/) e [161023](resultados/20261106-161023-02-pedidos-join/). O p95 mediano da rota foi 11.155,5 ms.
- **Depois:** três execuções de `03-indices-pedidos-cliente`: [161856](resultados/20261106-161856-03-indices-pedidos-cliente/), [162035](resultados/20261106-162035-03-indices-pedidos-cliente/) e [162210](resultados/20261106-162210-03-indices-pedidos-cliente/). Todas tiveram `0.00%` de erros e “Contrato mantido”. O plano após a mudança e o tamanho dos índices estão em [04-planos-indices-depois.txt](diagnostico/04-planos-indices-depois.txt).
- **Status:** aplicada e medida.
- **Conclusão:** comparada à versão com JOIN, a mediana passou de 4,21 para 6,25 requisições/s (+48,5%); o p95 geral caiu de 10.916,1 ms para 9.058 ms (-17,0%); e o p95 de `/clientes/:id/pedidos` caiu de 11.155,5 ms para 4.345,1 ms (-61,1%). O plano de uma execução da consulta mudou de leituras sequenciais de tabelas para buscas pelos dois novos índices; o tempo de execução nesse diagnóstico caiu de 4.706,174 ms para 1,179 ms. O custo medido dos índices foi 51 MB em disco (32 MB + 19 MB). A CPU média do banco permaneceu perto de 100%, o pico mediano de memória do banco foi 497,8 MiB de 512 MiB, e a memória média da API subiu de 34,8 para 71,5 MiB conforme a vazão aumentou. O ganho de latência nesta rota é claro, mas a saturação de CPU continua e o uso de memória precisa ser acompanhado.

## 04 — Índice para pedidos por status

- **Hipótese:** um índice B-tree em `pedidos(status, criado_em DESC, id DESC)` deve acelerar a contagem e a paginação por status, evitando leituras sequenciais e ordenação externa, principalmente nas páginas mais distantes. O custo é espaço em disco e manutenção do índice.
- **Evidência anterior:** [planos antes do índice](diagnostico/05-planos-status-antes.txt). A contagem por status levou 985 ms com leitura sequencial; a primeira página levou 1.105 ms com leitura e ordenação paralelas; a página 15.000 levou 3.112 ms e usou cerca de 90 MB de arquivos temporários para ordenação externa.
- **Fonte da hipótese:** [documentação PostgreSQL 16 — índices](https://www.postgresql.org/docs/16/indexes.html) descreve o ganho de leitura e o custo adicional de índices; [tipos de índice](https://www.postgresql.org/docs/16/indexes-types.html) explica que B-tree atende comparações de igualdade e pode fornecer linhas em ordem.
- **Antes:** três execuções de `03-indices-pedidos-cliente`: [161856](resultados/20261106-161856-03-indices-pedidos-cliente/), [162035](resultados/20261106-162035-03-indices-pedidos-cliente/) e [162210](resultados/20261106-162210-03-indices-pedidos-cliente/). O p95 mediano de `/pedidos?status=&pagina=` foi 10.675,4 ms.
- **Depois:** três execuções de `04-pedidos-status-index`: [163111](resultados/20261106-163111-04-pedidos-status-index/), [163247](resultados/20261106-163247-04-pedidos-status-index/) e [163426](resultados/20261106-163426-04-pedidos-status-index/). Todas tiveram `0.00%` de erros e “Contrato mantido”. Os planos e o tamanho do índice estão em [06-planos-status-depois.txt](diagnostico/06-planos-status-depois.txt).
- **Status:** aplicada e medida.
- **Conclusão:** comparada à versão anterior, a mediana passou de 6,25 para 10,13 requisições/s (+62,1%); o p95 geral caiu de 9.058 ms para 6.202 ms (-31,5%); e o p95 da rota por status caiu de 10.675,4 ms para 6.582,4 ms (-38,3%). O plano da primeira página passou a usar o índice e caiu de 1.105 ms para 0,231 ms; a contagem continuou custosa, caindo de 985 para 924 ms. A página 15.000 ainda escolheu leitura sequencial e ordenação externa: no diagnóstico pós-índice levou 5.099 ms, contra 3.112 ms antes, então paginação profunda permanece um gargalo. O índice ocupa 21 MB. A CPU média do banco continuou perto de 100% (mediana 99,8% antes e 99,7% depois); o pico mediano de memória caiu de 497,8 para 478,3 MiB, com variação entre execuções. O índice melhorou o conjunto medido, sobretudo a primeira página, mas não resolveu contagem nem páginas profundas.

## 05 — Remover coluna não usada em vendas por dia

- **Hipótese:** retirar `p.observacoes` da consulta deve reduzir os dados enviados pelo PostgreSQL e processados pelo Node.js, diminuindo o p95 e o uso de memória da rota, sem mudar a resposta, pois a coluna não é usada no agrupamento nem no JSON.
- **Evidência anterior:** [plano da consulta antes da mudança](diagnostico/07-vendas-por-dia-antes.txt) seleciona 12.945 linhas para sete dias e estima largura de 296 bytes; o código não lê `observacoes` depois da consulta. A leitura sequencial de `pedidos` será tratada separadamente.
- **Fonte da hipótese:** [documentação PostgreSQL 16 — listas de seleção](https://www.postgresql.org/docs/16/queries-select-lists.html) explica que a lista `SELECT` determina quais colunas são emitidas como resultado. A redução de latência nesta aplicação é uma hipótese a medir.
- **Antes:** três execuções de `04-pedidos-status-index`: [163111](resultados/20261106-163111-04-pedidos-status-index/), [163247](resultados/20261106-163247-04-pedidos-status-index/) e [163426](resultados/20261106-163426-04-pedidos-status-index/). O p95 mediano de `/relatorios/vendas-por-dia` foi 10.054,5 ms.
- **Depois:** três execuções de `05-vendas-sem-observacoes`: [165357](resultados/20261106-165357-05-vendas-sem-observacoes/), [165536](resultados/20261106-165536-05-vendas-sem-observacoes/) e [165713](resultados/20261106-165713-05-vendas-sem-observacoes/). Todas tiveram `0.00%` de erros e “Contrato mantido”. O plano depois da mudança está em [08-vendas-por-dia-depois.txt](diagnostico/08-vendas-por-dia-depois.txt).
- **Status:** aplicada e medida.
- **Conclusão:** comparada à versão anterior, a mediana passou de 10,13 para 12,87 requisições/s (+27,1%); o p95 geral caiu de 6.202 ms para 4.003,2 ms (-35,5%); e o p95 de `/relatorios/vendas-por-dia` caiu de 10.054,5 ms para 5.451,9 ms (-45,8%). O plano mudou de leitura sequencial para leitura somente do índice `idx_pedidos_status`; a largura estimada das linhas caiu de 296 para 20 bytes. A execução do `EXPLAIN ANALYZE` caiu de 226 para 194 ms, mas é uma amostra única e não substitui a comparação de carga. A CPU do banco permaneceu perto de 100%; o pico mediano de memória do banco variou de 478,3 para 497,5 MiB, enquanto a memória média da API caiu de 43,9 para 32,0 MiB. A mudança melhorou a rota sem criar índice adicional; o filtro por data ainda percorre o índice e merece um experimento separado.

## 06 — Diagnóstico temporário com 2 CPUs no banco

- **Hipótese:** se a CPU do banco for o gargalo principal na carga atual, duplicar temporariamente seu limite de 1 para 2 CPUs deve aumentar a vazão e reduzir a latência. O teste mantém memória, API, código, dados e parâmetros da carga iguais. O custo operacional também dobra o limite de CPU do banco durante este diagnóstico. Como a porta 5432 do host está ocupada pelo PostgreSQL local, o Compose publica temporariamente o banco em 5433; a comunicação interna da API continua em 5432.
- **Antes:** três execuções de `05-vendas-sem-observacoes`: [165357](resultados/20261106-165357-05-vendas-sem-observacoes/), [165536](resultados/20261106-165536-05-vendas-sem-observacoes/) e [165713](resultados/20261106-165713-05-vendas-sem-observacoes/), com limite de banco de 1 CPU.
- **Depois:** três execuções com 2 CPUs: [111438](resultados/20261109-111438-06-banco-2-cpus/), [111612](resultados/20261109-111612-06-banco-2-cpus/) e [111745](resultados/20261109-111745-06-banco-2-cpus/). Todas tiveram `0.00%` de erros e “Contrato mantido”.
- **Conclusão:** a mediana subiu de 12,87 para 24,05 requisições/s (+86,9%) e o p95 geral caiu de 4.003,2 para 2.117,8 ms (-47,1%). A CPU média mediana do banco passou de 100,3% para 200,4%, usando os dois núcleos disponíveis. O teste confirma que o limite de 1 CPU restringia a vazão nessa carga: dar mais CPU ao banco quase dobrou o desempenho, com custo correspondente de até mais um núcleo. O pico de memória mediano foi 473,9 MiB, abaixo do limite de 512 MiB. Esta é uma medição local, não uma proposta para deixar o limite aumentado; ele será restaurado para 1 CPU. O banco do Compose permanece publicado na porta local 5433, pois a porta 5432 está ocupada pelo PostgreSQL 18 instalado no host.
- **Status:** medido; limite de CPU restaurado após o experimento.

## 07 — Diagnóstico de consultas com pg_stat_statements

- **Objetivo:** identificar quais instruções SQL acumulam mais tempo total e maior tempo médio durante a carga padrão, para escolher a próxima otimização com evidência.
- **Método:** habilitar temporariamente `pg_stat_statements`, zerar as estatísticas antes das execuções, rodar três medições com `VUS=20`, `DURACAO=60s` e `SEMENTE=42`, e salvar as instruções agregadas no diagnóstico. A instrumentação será removida depois da coleta.
- **Impacto:** recriar o volume PostgreSQL é necessário para aplicar o novo arquivo de inicialização; os dados fictícios são gerados novamente pelo próprio desafio.
- **Resultados:** três execuções em [113006](resultados/20261109-113006-07-estatisticas-consultas/), [113203](resultados/20261109-113203-07-estatisticas-consultas/) e [113346](resultados/20261109-113346-07-estatisticas-consultas/). Todas tiveram `0.00%` de erros e “Contrato mantido”. O resumo das consultas está em [09-consultas-pg-stat-statements.txt](diagnostico/09-consultas-pg-stat-statements.txt); os planos detalhados estão em [10-planos-consultas-mais-custosas.txt](diagnostico/10-planos-consultas-mais-custosas.txt).
- **Conclusão:** a mediana durante este diagnóstico instrumentado foi 13,36 req/s, p95 de 3.810,8 ms e CPU média do banco de 100,7%. Esses números não são comparação de performance com os experimentos anteriores: o volume foi recriado e as estatísticas incluem aquecimento e verificação do contrato. Nas três rodadas, `top-produtos` foi a consulta mais cara por chamada (média observada entre 9,15 e 11,21 s, com uma amostra de `EXPLAIN ANALYZE` em 14,69 s). O plano junta e agrega todos os itens; a varredura paralela lê 500 mil itens por worker. É a próxima candidata a otimização. `vendas-por-dia` também filtra muitos pedidos: o plano removeu 165.229 linhas por worker e levou 245 ms nesta amostra isolada. A página profunda por status usou `idx_pedidos_status` e levou 55 ms nessa amostra; as estatísticas agregadas mostram que a rota ainda soma tempo sob carga, então uma medição isolada não a elimina como alvo.
- **Status:** diagnóstico concluído; extensão e configuração temporárias removidas. A evidência foi usada no experimento 08.

## 08 — Pré-computar os totais de top produtos

Como a API não tem rotas de escrita, os dados da visão permanecem sincronizados com o conjunto estático do desafio.
- **Antes:** três medições limpas com 1 CPU no banco, limite de memória inalterado, `VUS=20`, `DURACAO=60s` e `SEMENTE=42`: [120602](resultados/20261109-120602-08-top-produtos-antes/), [120735](resultados/20261109-120735-08-top-produtos-antes/) e [120917](resultados/20261109-120917-08-top-produtos-antes/). Todas tiveram `0.00%` de erros e “Contrato mantido”. Medianas: 13,31 req/s; p95 geral 4.395,0 ms; p95 da rota top produtos 23.701,1 ms; CPU média do banco 100,0%.
- **Mudança:** visão materializada `resumo_top_produtos` e índice pela ordem do relatório; a rota lê a visão com o mesmo `ORDER BY` e `LIMIT`. O contrato passou nas 42 respostas após corrigir o mapeamento do id.
- **Depois:** três medições com os mesmos parâmetros: [121340](resultados/20261109-121340-08-top-produtos-depois/), [121509](resultados/20261109-121509-08-top-produtos-depois/) e [121638](resultados/20261109-121638-08-top-produtos-depois/). - **Conclusão:** comparada à referência, a mediana subiu de 13,31 para 26,17 req/s (+96,6%) e o p95 geral caiu de 4.395,0 para 1.891,2 ms (-57,0%). O p95 da rota top produtos caiu de 23.701,1 para 581,5 ms (-97,5%). Uma execução de `EXPLAIN ANALYZE` caiu de 14.693,470 ms na consulta original para 0,097 ms lendo a visão; são amostras isoladas, enquanto as três cargas sustentam a comparação geral. O banco continuou perto de 100% de CPU (medianas 100,0% antes e 100,2% depois), mas processou quase o dobro da vazão; a memória média mediana caiu de 367,1 para 213,3 MiB e o pico mediano de 491,7 para 244,3 MiB. A visão tem 19.206 linhas e ocupa 1.728.512 bytes, o índice 622.592 bytes e o conjunto 2.392.064 bytes (2.336 kB). O tempo adicional de inicialização para gerar a visão não foi medido separadamente. A visão só fica atualizada quando recriamos o banco; isso é adequado para os dados estáticos e a API somente leitura deste desafio, mas precisaria de atualização se houvesse escrita de pedidos ou itens.
- **Status:** aplicada, validada e medida; commits locais separados para hipótese/código e resultados.

## 09 — Usar intervalo direto de timestamp no relatório diário

O tipo da coluna é `timestamp` sem fuso. Esta etapa altera somente a consulta da rota; qualquer índice será avaliado separadamente.
- **Antes:** três medições com a configuração atual e `VUS=20`, `DURACAO=60s`, `SEMENTE=42`: [125512](resultados/20261109-125512-09-filtro-data-antes/), [125640](resultados/20261109-125640-09-filtro-data-antes/) e [125808](resultados/20261109-125808-09-filtro-data-antes/). - **Mudança:** filtro da consulta reescrito para intervalo semiaberto; nenhum índice ou outro código foi alterado.
- **Depois:** três medições com os mesmos parâmetros: [130035](resultados/20261109-130035-09-filtro-data-depois/), [130202](resultados/20261109-130202-09-filtro-data-depois/) e [130329](resultados/20261109-130329-09-filtro-data-depois/). - **Conclusão:** a mediana subiu de 27,43 para 30,88 req/s (+12,6%); o p95 geral caiu de 1.698,6 para 1.407,5 ms (-17,1%); e o p95 de `vendas-por-dia` caiu de 2.583,6 para 1.854,1 ms (-28,2%). A CPU média mediana do banco passou de 100,8% para 100,3%, ainda no limite. No plano isolado, o filtro passou de `Filter` com cast na coluna e 165.229 linhas removidas por worker para `Index Cond` pelo intervalo de data, com 160 linhas canceladas removidas por worker; o tempo de execução caiu de 245,306 para 138,087 ms (-43,7%). Nenhum índice adicional foi criado. A reescrita melhorou a rota e a vazão sem custo de armazenamento adicional; a CPU geral continua saturada porque a capacidade liberada foi usada para atender mais carga.
- **Status:** aplicada, validada e medida; sem índice novo.
